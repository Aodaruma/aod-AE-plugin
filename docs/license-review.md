# ライセンス方針の検討メモ

調査日: 2026-09-06。対象: 取得時点の `origin/dev`、コミット `d0be3a3b18cd6ada94de09408c5b95566c803e56`。
作業ブランチ: `codex/clarify-plugin-licensing`。

これは変更前の状態を記録した調査メモであり、新たな利用許諾を付与する文書ではありません。調査後、A案に沿って追加許諾と生成・配布処理の更新を実施しました。現在の利用条件は [LICENSING.md](../LICENSING.md) と、そこから参照する許諾本文を確認してください。以下の「現状」は上記調査コミット時点の状態です。

現在の「生成した独自プラグインを非公開で配布してよい」という意図は、リポジトリの表記から十分には読み取れません。とくにテンプレートの実装が生成後のソースへコピーされるため、README に利用方針を書き足すだけでなく、そのコードに適用する許諾を明確にする必要があります。

**確認した事実**

| 対象 | 現状 | 問題・意味 |

Cargo の継承には各パッケージで `license.workspace = true` が必要です。ただし、メタデータが空でも既存のソースに対するライセンスが消えるわけではありません。[Cargo 公式: workspace.package](https://doc.rust-lang.org/cargo/reference/workspaces.html#the-package-table)

実生成は `cargo-generate 0.23.7` で、`features = []` と `features = ["wgpu"]` の2通りを確認しました。CPU は5ファイル、GPU は8ファイルを出力し、GPU の WGSL もテンプレートからコピーされます。Rhai の pre/post フックと生成設定は出力されません。生成物は Git 管理外の `target/license-review/generated/` に保持しています。今回は生成される内容の確認が目的で、AE プラグインのコンパイル・実機動作は検証していません。

リリースについて確認したのは workflow の実装です。公開済み ZIP やリリースページ全体の実査はしておらず、この事実だけで既存配布の違反とは断定しません。

**MPL と今回の構造をどう読むか**

MPL はファイル単位のコピーレフトです。MPL コードへの変更や、それを含む新規ファイルが対象になります。MPL コードを含まない別ファイルの独自実装は、同じバイナリに結合しても非公開にできます。静的リンクも、それだけで独自コード全体の公開を要求するものではありません。[Mozilla FAQ Q11–Q12](https://www.mozilla.org/en-US/MPL/2.0/FAQ/)

したがって、`utils` を依存クレートとして呼び出す場合と、テンプレートの実装を `src/lib.rs` に取り込む場合は別に考える必要があります。後者は [LICENSE](../LICENSE) 1.4・1.10 の定義に照らすと、生成ファイルが MPL 対象になると読む根拠があります。これは条文と実装からの評価であり、個々のコードの著作物性についての法的確定判断ではありません。「cargo generate を実行した」という操作自体が問題なのではなく、出力に何のコードが含まれるかが問題です。

生成ツールと出力を別に許諾する実例として GNU Bison があります。Bison は実装の一部を出力へコピーするため、生成パーサーを非自由ソフトウェアでも使えるよう例外を用意しています。ただしこれは GPL 向けの例であり、その例外文を MPL にそのまま流用できるという意味ではありません。[GNU Bison: Conditions](https://www.gnu.org/software/bison/manual/html_node/Conditions.html)

「MPL に従って公開してほしい」は、次の範囲に言い換えると正確になります。

- 組織外へバイナリを配布する場合、含まれる MPL 対象部分のソースを、配布先が合理的な方法で取得できるようにして、その方法を知らせる。変更していない MPL 部分も対象です。
- 改変した対象ファイルのソースは改変内容を含めて提供する。差分だけ、本家の未改変ソースだけでは代替できません。
- 世界中に公開すること、本家へ PR を送ること、独自実装を含む全リポジトリを公開することまでは要求しません。対象ソースについて受領者が持つ MPL の権利も制限できません。
- 私的利用・組織内利用だけなら、この配布によるソース提供義務は生じません。改良した生成ツールを内部で使うだけの場合も、改良版ツールそのものの配布とは区別します。

根拠は [MPL 2.0 第3条](https://www.mozilla.org/en-US/MPL/2.0/#3-responsibilities) と [Mozilla FAQ Q5–Q10](https://www.mozilla.org/en-US/MPL/2.0/FAQ/) です。「改良は必ず一般公開」「別ファイルで追加した機能もすべて公開」が必須なら、通常の MPL より強い要求になります。

**改善案の比較**

| 案 | 独自プラグインの非公開配布 | テンプレート自体の改良版の配布 | 評価 |
| --- | --- | --- | --- |
| A. MPL を維持し、指定テンプレートのプラグイン生成用途に追加許諾 | 追加許諾の範囲で可能 | テンプレートとして配布する改良は MPL に残す設計 | 今回の意図に最も近い。用途の境界と許諾文の検討が必要 |
| B. 生成される雛形コードを MIT 等で別途許諾し、utils と既存プラグインは MPL | 可能。表示等の条件は残る | 寛容な許諾を受けた雛形部分の改良は非公開配布も可能 | 標準ライセンスで説明しやすいが、テンプレート改良の還元は保証しない |
| C. MPL のまま説明だけ追加し、独自処理を別ファイルに分離 | MPL コードを含まないファイルは可能 | MPL を維持 | 部分的な整理。生成されたファイルも含めて非公開にしたい意図は満たさない |
| D. リポジトリ全体を MIT 等に変更・デュアルライセンス化 | 可能 | utils・既存プラグインの改良まで非公開にできる | 今回の意図に合わない |

B の場合、実行用の Rhai フックなどを MPL のまま分離することはできます。しかし、生成コードの本体を MIT 等で許諾する以上、その部分をテンプレートとして改良する場合にも寛容な許諾を利用できます。「MIT OR MPL-2.0」も MIT を選べるため、この点は解決しません。

**推奨する A 案の範囲**

テンプレートの改良版を配布する場合も MPL に残したいという意図を優先し、A 案を第一候補とします。以下は許諾文に盛り込む設計要件であり、確定した条文ではありません。

- ルートの MPL 本文を改変せず、権利者による追加許諾を別文書にする。README にその存在と対象を明記する。
- 許諾対象は、指定された生成用ファイルからプラグインへ取り込まれたコードと、そのプラグイン内での改変。独自プラグインのソース非公開、商用利用、有償・無償のバイナリ配布、継続改良を許容する。
- 対象を `src/lib.rs` だけに絞らず、`build.rs`、`Justfile`、manifest、README、GPU モジュール、WGSL まで棚卸しする。
- フレームワーク・テンプレートとしての再配布、`crates/utils/`、既存プラグイン固有の実装、第三者コードは追加許諾の対象にしない。
- ファイルを `templates/` に移動したり、既存プラグインを生成工程に通したりしても、追加許諾の対象を増やせないよう、由来・対象ファイル・適用版を定める。
- 生成後に独自コードを追記しても非公開配布の許可が続くことと、生成物を別のフレームワーク／テンプレートとして再配布する場合の扱いを分けて定義する。
- 必要な著作権・許諾・免責表示とその添付方法を定め、生成物にも許諾を持ち出せるようにする。「非公開でよい」を「通知義務も何もない」と説明しない。

| A 案導入後の利用例 | 想定する扱い |
| --- | --- |
| 雛形から独自のエフェクトを開発して販売 | 生成物内の独自実装を非公開にできる。生成用コードの追加許諾と依存ライセンスを遵守 |
| そのエフェクトで未改変 utils を利用 | 独自実装は非公開にできる。バイナリに含まれる utils の対応ソースと取得方法を案内 |
| utils の処理を改変して、組み込んだバイナリを配布 | 改変した utils の MPL 対象ソースを提供。独自ファイルまで一律に提供する必要はない |
| 既存プラグインの実装ファイルを改変・コピーして配布 | その MPL 対象ファイルに通常の義務。追加許諾の対象にはならない |
| 改良したテンプレートを他の開発者に配布 | テンプレート自体は MPL。ソース形式なら改良版を MPL で配布 |
| 改良したテンプレートを内部だけで使って独自プラグインを生成 | ツール自体を配布していなければ、その非公開改良の提供までは通常の MPL で要求できない。生成物については追加許諾の条件を適用 |

utils を未改変で使う場合は、使用版に対応する取得可能なソースへのリンクを案内する運用が考えられます。単に動き続ける `dev` の URL を置くより、コミットやタグで版を特定し、配布先が実際に取得できる状態を維持する方が明確です。

**実装時に変更する候補**

1. 追加許諾の文書と対象ファイル一覧を追加する。テンプレートのソースと生成結果の両方から参照できるようにし、出力に MPL 限定と誤読する表示だけが残らないようにする。
2. ルート README に日英の利用例を追加する。独自プラグイン、utils、既存プラグインのコピー、テンプレート再配布の4ケースを説明する。
3. 既存38プラグインと utils に `license.workspace = true` を追加する。適切なソースヘッダーまたはディレクトリ単位の通知も整備する。
4. 生成テンプレートでは既存プラグイン用の MPL 指定を機械的に継承させず、外部用／リポジトリへの投稿用で説明・設定を分ける。生成側が選ぶライセンスと、同梱したコードの許諾は別に記録する。
5. 独自の追加許諾を標準 SPDX 例外と誤認させる識別子は作らず、必要なら Cargo の `license-file` 等で全文を示す。独自コードを含むプロジェクト全体のライセンスをテンプレート側で勝手に決めない。[Cargo 公式: license / license-file](https://doc.rust-lang.org/cargo/reference/manifest.html#the-license-and-license-file-fields)
6. 生成される作者・著作権・サポート先を外部開発者向けに設定可能にする。既存プラグインの Match Name は変更しない。
7. リリース ZIP にライセンス類、使用コミット、対応ソース取得先、必要な第三者通知を加える。
8. 投稿ルールに、通常部分は MPL、対象テンプレートへの寄与には追加許諾も適用することを明示する。新規投稿を受け入れる際に、この許諾が継続するよう確認する。

生成プラグインは現在 `../../crates/utils` やルートの `AdobePlugin.just` に依存します。非公開開発の案内には、別 workspace へ持ち出す手順か、フォーク内で独自ファイルを明示的に区別する手順も必要です。ビルド専用のツールを利用しただけでプラグイン全体が MPL になるとは扱わず、それらをソースとして再配布する場合の条件を説明します。

**採用前に詰める事項と調査の限界**

テンプレートの Git 履歴には Aodaruma 名義の18コミットを確認しましたが、Git の著者情報だけでは、コードの権利や第三者からの流用がないことを証明できません。追加許諾を出せる権利者と、許諾対象の由来を確認する必要があります。第三者のコードまでリポジトリ所有者の判断で緩和することはできません。[Mozilla Relicensing FAQ](https://www-archive.mozilla.org/mpl/relicensing-faq)

固定された依存リビジョン `0e0b197850f28c1bb24e8c82fce2e3d4c120d1e9` の manifest では、`after-effects` は `Apache-2.0 OR BSD-3-Clause OR MIT OR Zlib`、`pipl` は `MIT OR Apache-2.0` です。これらの表示は本リポジトリの MPL と別です。今回、全推移依存や Adobe SDK の配布条件までは精査していません。[after-effects の該当 manifest](https://github.com/virtualritz/after-effects/blob/0e0b197850f28c1bb24e8c82fce2e3d4c120d1e9/after-effects/Cargo.toml)、[pipl の該当 manifest](https://github.com/virtualritz/after-effects/blob/0e0b197850f28c1bb24e8c82fce2e3d4c120d1e9/pipl/Cargo.toml)

過去のテンプレートから生成済みのプラグインにも適用する場合は、対象となる過去版と権利範囲を指定する必要があります。新しい表記を追加しただけで、全過去版・全寄与者のコードに自動的に許諾が及ぶとは扱いません。既存の MPL で取得した権利を取り消す変更にもできません。

最終的な分岐は、テンプレート本体の改良還元まで維持する A 案か、生成用雛形に限ってその条件を緩め、標準ライセンスで運用できる B 案かです。現在の要望は A 案として解釈しています。A 案では生成物とテンプレート再配布の境界が許諾の実効性を左右するため、正式採用前に、具体的な文面をオープンソースライセンスに詳しい法律専門家に確認するのが適切です。
